## 已解決：學生改得動自己那一列的 risk_* 欄位（2026-09-21，走解法甲）

`hc_health_selfcheck` 上學生的 policy 是 **ALL**（自己那一列全開），而 RLS
只能限制「哪幾列」、不能限制「哪幾欄」——所以會開開發者工具的學生本來可以
直接送 update 把 `risk_reviewed` 改成 true、`risk_level` 改成 0，旗子就不見了。

蕾蕾 2026-09-21 決定走甲：
> 理由不是風險高低，是後果不成比例——能把自己的求救訊號關掉的系統，
> 等於沒有那個機制。會開開發者工具的學生不多，但只要有一個、而且剛好是
> 勾了第 20 題那個，我就永遠不會知道。

乙（判定規則也搬進 SQL）不做：規則會變成兩份，改門檻要同步兩邊，本身是新的風險。

實作：`supabase/migrations/20260921000000_lock_risk_columns.sql`，
BEFORE INSERT OR UPDATE 的 `hc_guard_risk` trigger，只對 **PostgREST 直送的寫入**
（`current_user = 'authenticated'`）生效。擋法是把值還原成舊值，不是 raise——
學生按下送出的那一刻可能正好是他剛勾完第 20 題，那時候讓儲存失敗是最糟的結果。

| 欄位 | 規則 |
|---|---|
| `risk_reviewed` / `risk_reviewed_at` / `risk_outcome` / `risk_note` | 只有 `hc_health_risk_review()` 改得動；新增時一律清成未處理 |
| `depression_critical` | 黏性下放到資料庫（原本只在前端執行，繞過前端就沒了） |
| `risk_level` / `risk_l3_count` | 只能往上，不能往下 |
| `risk_flagged_at` | 可以往後更新（升級時），不能清成 null |
| 作答欄位（分數、量表內容） | **完全不管**，重新作答照常 |

⚠️ **這一條有一個真的行為改變**：學生重做之後分數變低時，等級不會跟著降，
`risk_level` 的語意變成「這學期判定過的最高等級」。資料庫分不出「誠實重測算出來的
1」與「自己改成的 1」，要分得出來只有解法乙。教師端紅旗卡片因此會多一行
「最近一次作答重算是 ◯◯」，避免出現「標著需關注、底下的分數卻不到」。
關掉個案的方式是「已聯繫」，不是等等級自己降。

`hc_guard_risk_columns()` **必須是 security invoker**（預設）。寫成
SECURITY DEFINER 的話 `current_user` 會變成函式擁有者，那個判斷就永遠成立，
等於沒擋。

`needs_followup` 沒有動：教師端已經全部改看 `risk_level`，那個舊布林值
現在沒有任何畫面在讀。

## 中優先：hc_classes 的 WITH CHECK 沒有檢查 hc_teachers

```sql
-- 目前的 policy
hc_classes_owner  ALL  WITH CHECK (teacher_id = auth.uid() OR hc_is_admin())
```

這條**完全沒有查 `hc_teachers`**。任何登入成功的帳號（含學生）只要能叫到
PostgREST，就可以插入一列 `teacher_id = auth.uid()` 的班級；插進去之後
`hc_owns_class()` 對那個班就成立，接著可以加學生、開課堂、記出缺席。

2026-09-12 刪掉三列誤建的 `hc_teachers`（s310055／s310189／s310247，
三位都是學生，0 個班級）之後，他們的畫面不再是教師後台了。
但那是**關門，不是上鎖**——門閂還在門外。

### 為什麼不急

- RLS 仍然把讀取範圍框死在「自己建的」。實測過：用那三個帳號的身分查詢，
  班級／學生／自我檢測全是 0，`hc_teaches_student_email(別人)` 回 false。
  **讀不到任何別人的資料，不會外洩。**
- 最壞的情況是資料表長出沒人要的垃圾班級。
- 而且現在學生登入後會被導到 `/health`，看不到建班的介面，要刻意繞才做得到。

### 要動的時候要注意

改 WITH CHECK 加上「必須是 hc_teachers 裡的人」是一個 migration，
會動到**所有人的建班路徑**。動之前要先確認沒有別的流程依賴現在的寬鬆條件
（例如老師第一次登入時 `hc_ensure_teacher()` 與第一次建班的先後順序）。
還沒查過，不要憑印象改。

### 學生端年級：白名單放進非高三班級之前要先處理

`hc_my_student_profile()` 沒有回傳 grade，而學生讀不到 `hc_classes`
（RLS 只開給帶班的老師），所以學生端目前用 `rules.ts` 的 `STUDENT_GRADE = 3`。

**現在不急，因為健康模組白名單（`hc_classes.health_enabled`）裡只有
305–309 五個高三班。** 學生端會看到的年齡列因此一定是對的。

⚠️ **未來如果把其他年級的班級加進白名單，一定要先改
`hc_my_student_profile()` 讓它回傳年級**，否則高一高二的學生會被套上
高三（17／18 歲）的 BMI 門檻。15 歲那列過重是 22.9、18 歲是 24.0，
差 1.1，會把正常的判成過重。

改法：那支函式已經 join 了 `hc_classes`，多回一欄 `c.grade`
（順便可以回 `c.grade_confirmed`）。注意那是 DROP + CREATE——
PostgreSQL 不能用 CREATE OR REPLACE 改 RETURNS TABLE 的欄位——
改完要補回原本的
`revoke execute ... from public, anon` 與 `grant execute ... to authenticated`。

## 已定案：教師端的紅／琥珀分層原則

**紅色＝今天要處理**（血壓、血氧、脈搏：請學生休息後重測，必要時當天帶去保健室）。
**琥珀＝長期指標，課堂上談**（BMI、體脂率、腰圍、腰臀比）。
加新欄位時照這個問題判斷：「看到這個數字，老師今天做得了什麼？」
做得了 → 紅，做不了 → 琥珀。實作在 `src/health/teacher/thresholds.ts`。

體脂率與腰圍的門檻（2026-09-20 由蕾蕾提供，當天又修正過兩處）：
體脂率只標偏高那一側（> 20% 略高、≥ 25% 偏高），課本的「14–20% 正常」
那一段的**偏低側不標**——那是 30 歲以下成人的範圍，用在發育中的高中男生
會大量誤判，而且偏低不是這群人要提醒的方向。
腰圍用 **≥ 90**（國健署代謝症候群的判定門檻），剛好卡 90.0 的那 7 個人也標起來。

（下面是當初提出這件事時的實測數字，留著當背景。）
用 2026-09-19 的 158 筆期初資料實算：

| 項目 | 紅（≥23.2） | 琥珀（21.9–23.2） | 偏低（<17.7） |
|---|---|---|---|
| BMI | 60 人 | 18 人 | 16 人 |

整列被標紅的比例：305 有 12/27、306 有 14/32、307 有 14/27、308 有 17/36、309 有 15/35，
**大約每兩人就有一人**。其中絕大多數是 BMI 造成的——把 BMI 拿掉只剩 2～7 人／班。
原型用的成人門檻 27 則是 1～7 人／班。

選的是方向二（教師端 BMI 只標琥珀）。理由不是紅標太多，是紅色的定義應該是
「今天要處理」，BMI 是長期指標，不需要當天行動。
